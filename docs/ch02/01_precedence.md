# 01 — 文法が優先順位を決める

`2 + 3 * 4` が `14` になるか `20` になるかは、文法の書き方で決まる。これがこの章の中心テーマだ。

## 1. ナイーブな書き方の問題

最初に「素朴に書いたらどうなるか」を見ておく。仮に bison でこう書いたとする。

```yacc
expr
    : INT_LIT
    | expr '+' expr
    | expr '-' expr
    | expr '*' expr
    | expr '/' expr
    ;
```

「式は整数か、式と式を演算子でつなげたもの」── 直感的だ。だが、これは**曖昧 (ambiguous)** だ。

入力 `2 + 3 * 4` に対して、bison は2通りの解釈ができてしまう。

```
解釈A:  expr             解釈B:  expr
        / | \                    / | \
     expr + expr             expr * expr
       2  / | \              / | \   4
        expr * expr        expr + expr
          3     4            2     3
```

A なら `2 + 12 = 14`、B なら `5 * 4 = 20`。bison は「どちらでも文法的に正しい」と判断し、競合 (shift/reduce conflict) を報告する。我々の意図（A）は伝わらない。

これを解決する方法は2つある。

1. bison の `%left` 宣言で優先順位と結合性を指定する（手軽だが、文法の構造に表れない）。
2. **文法の階層そのもので優先順位を表現する**。

この章では (2) を選ぶ。文法を読めば優先順位がそのまま見えるからだ。これは BNF (Backus-Naur Form) の伝統的な書き方で、教科書でもよく出てくる形だ。

## 2. 階層化された文法

優先順位の階層をそのまま文法の階層にする。

```yacc
expr     : add_expr ;

add_expr : mul_expr
         | add_expr '+' mul_expr
         | add_expr '-' mul_expr
         ;

mul_expr : unary
         | mul_expr '*' unary
         | mul_expr '/' unary
         | mul_expr '%' unary
         ;

unary    : primary
         | '-' unary
         ;

primary  : INT_LIT
         | '(' expr ')'
         ;
```

この5階層の文法が、優先順位の表を**そのまま** 表している。

| 階層 | 含まれる演算子 | 優先順位 |
|------|--------------|---------|
| `primary` | （リテラルと括弧） | （葉） |
| `unary` | `-` (単項) | 高い |
| `mul_expr` | `* / %` | 中 |
| `add_expr` | `+ -` | 低い |
| `expr` | （`add_expr` と同じ） | エントリポイント |

階層が深いほど、強く結びつく。

階層の上下関係はこうなっている。

```
add_expr   → ... → mul_expr → unary → primary
  +  -              *  /  %     -      INT_LIT, ( expr )
```

つまり、`add_expr` のオペランドは `mul_expr` であり、`mul_expr` のオペランドは `unary` である。**強い演算子のほうが、葉に近い側にいる**。

## 3. なぜこれで優先順位が出るのか

`2 + 3 * 4` を、この文法で展開してみよう。bison は **ボトムアップ**（下から組み立てる）パーサだが、頭の中では**上から下に展開する**ほうが分かりやすい。

エントリ `expr` から始めて、入力の各部分を文法のどの階層で受け入れるかを決めていく。

```
expr
└─ add_expr
   ├─ add_expr   ← "2"  これは mul_expr → unary → primary → INT_LIT(2) でしか受からない
   │  └─ mul_expr
   │     └─ unary
   │        └─ primary
   │           └─ INT_LIT 2
   ├─ '+'
   └─ mul_expr   ← "3 * 4"  これは mul_expr の規則 mul_expr '*' unary に当てはまる
      ├─ mul_expr
      │  └─ unary
      │     └─ primary
      │        └─ INT_LIT 3
      ├─ '*'
      └─ unary
         └─ primary
            └─ INT_LIT 4
```

ポイントは、`+` の右側にある `3 * 4` が **`mul_expr` として受け取られる** こと。`mul_expr` は `*` を含めて1つの塊として組み立てられる。だから `+` の右オペランドが `(3 * 4)` という塊になる。

逆方向、つまり `2 * 3 + 4` だとどうなるか。

```
expr
└─ add_expr
   ├─ add_expr     ← "2 * 3"  これは mul_expr の規則 mul_expr '*' unary に当てはまる
   │  └─ mul_expr
   │     ├─ mul_expr
   │     │  └─ unary
   │     │     └─ primary
   │     │        └─ INT_LIT 2
   │     ├─ '*'
   │     └─ unary
   │        └─ primary
   │           └─ INT_LIT 3
   ├─ '+'
   └─ mul_expr   ← "4"
      └─ unary
         └─ primary
            └─ INT_LIT 4
```

今度は `2 * 3` が左の塊になり、`+` で `4` と結ばれる。`*` の方が先に組み立てられるから、優先順位が高い、というわけだ。

文法が階層になっているから、**強い演算子は内側で必ず先に塊になる**。これが「優先順位を文法で表現する」の核心だ。

## 4. 結合性も文法で決まる

`10 - 3 - 2` は、`(10 - 3) - 2 = 5` か、`10 - (3 - 2) = 9` か。C の規格では前者（左結合）。これも文法で表現できる。

`add_expr` の規則を見直そう。

```yacc
add_expr : mul_expr
         | add_expr '+' mul_expr
         | add_expr '-' mul_expr
         ;
```

二つ目と三つ目の規則。**左側が `add_expr`、右側が `mul_expr`** になっている。これが左結合の表現だ。

`10 - 3 - 2` を当てはめてみよう。

```
add_expr
├─ add_expr ← "10 - 3"
│  ├─ add_expr ← "10"
│  ├─ '-'
│  └─ mul_expr ← "3"
├─ '-'
└─ mul_expr ← "2"
```

「`add_expr` の左側にもう一段 `add_expr` がある」── これが左結合になる。再帰が左に伸びていく。

仮に右結合にしたければ、規則を裏返して `add_expr : mul_expr | mul_expr '+' add_expr` と書けばいい。すると右側に `add_expr` が伸び、`10 - (3 - 2)` になる。文法の書き方ひとつで結合性まで決まる。

C は加減と乗除は左結合なので、我々の文法もそうしている。

## 5. 単項マイナス

`unary` の階層を改めて見る。

```yacc
unary    : primary
         | '-' unary
         ;
```

「`unary` は、`primary` 単体か、または `-` の後にもう一段 `unary` を続けたもの」。これで `--5` のような連続にも対応する（実際に書く人はいないが、文法的には可能）。

`-(2 + 3)` のように、後ろに括弧つきの式が来る場合は、`unary → primary → '(' expr ')'` という経路で解釈される。`primary` が `'(' expr ')'` を受け入れるので、括弧の中身は再びフルの式に戻れる。これで括弧による優先順位の上書きも自然に表現できる。

## 6. 実際の AST の形

文法の階層は、AST の形に反映される。

入力 `2 + 3 * 4` のAST:

```
BINARY +
├─ INT_LIT 2
└─ BINARY *
   ├─ INT_LIT 3
   └─ INT_LIT 4
```

入力 `(2 + 3) * 4` のAST:

```
BINARY *
├─ BINARY +
│  ├─ INT_LIT 2
│  └─ INT_LIT 3
└─ INT_LIT 4
```

**括弧は AST には残らない**。括弧は文法を曖昧でなくするための記号で、いったん木が組み上がったら役目を終える。木の中で「先に計算するもの」は、葉に近い場所に座っている。

入力 `-(2 + 3)` のAST:

```
UNARY -
└─ BINARY +
   ├─ INT_LIT 2
   └─ INT_LIT 3
```

`UNARY` は子を1つしか持たない。`BINARY` は左右2つの子を持つ。AST のノード型としては別物にしてある（`ast.h` で `NODE_UNARY` と `NODE_BINARY` を定義する）。

## 7. parser.y アクション部

文法規則の右側に `{ ... }` でアクションを書くと、bison がその規則で還元 (reduce) するときに実行される。アクションの中で AST を組み立てていく。

```yacc
add_expr
    : mul_expr                  { $$ = $1; }
    | add_expr '+' mul_expr     { $$ = new_binary('+', $1, $3); }
    | add_expr '-' mul_expr     { $$ = new_binary('-', $1, $3); }
    ;
```

- `$1`, `$2`, `$3` は規則の右辺の各シンボルが持つ値（`%type` で型を宣言したもの）。
- `$$` は規則の左辺（この規則で作られた塊）に持たせる値。
- `mul_expr` 単体の規則では「右辺の値をそのまま左辺に渡す」だけ (`$$ = $1`)。
- 演算子つきの規則では `new_binary` で AST ノードを作る。

`new_binary('+', $1, $3)` は ast.c で定義したコンストラクタ。第1引数が演算子の文字、第2引数が左の子、第3引数が右の子（`$2` は `'+'` 自身なので不要）。

`unary` の `'-' unary` 規則も同様で、`new_unary('-', $2)` を呼ぶ。

`primary` の `'(' expr ')'` 規則は `$$ = $2` だけでいい。「括弧の中身（`expr`、つまり `$2`）をそのまま外側に渡す」。これで括弧は AST 上に残らず消える。

## 8. まとめ

- **文法の階層** = **優先順位の階層**。`expr → add_expr → mul_expr → unary → primary` と深くなるほど強い演算子。
- 規則の左に `add_expr` を持つことで **左結合** を表現する。
- `unary : '-' unary` のような **再帰的な単項規則** で連続適用も自然に書ける。
- 括弧 `( expr )` は **`primary` から `expr` に戻る抜け道**。優先順位を任意の場所で上書きできる。
- アクション `{ $$ = new_binary(...) }` で、文法の還元と同時に AST が育つ。
