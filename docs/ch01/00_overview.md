# 第1章 — 42を返すだけのコンパイラ

## 0. はじめに — この章だけは特別

これから C コンパイラを作る。ただし、いきなり全部は作らない。最初は**笑ってしまうほど小さなコンパイラ**から始めて、章が進むごとに少しずつ機能を足していく。

第1章で作るコンパイラがコンパイルできるのは、たった一種類のプログラムだけだ。

```c
int main() {
    return 42;
}
```

これだけ。足し算もできない。変数も使えない。`if` も `while` もない。`return` の後に書ける数字も整数リテラル一個だけ。

「そんなの作って何の意味があるの？」と思うかもしれない。でもこの小さなコンパイラには、本物のコンパイラが持つ要素がすべて入っている。

- ソースコードを読んで、文字をトークンに分解する（**字句解析**）
- トークン列の構造を理解して、木のかたちに組み立てる（**構文解析**）
- 木を辿って、x86 アセンブリを出力する（**コード生成**）

そして、出力されたアセンブリを `gcc` でリンクすれば、本当に動く実行ファイルができる。終了コードは 42 になる。

第2章以降では、この骨格に肉をつけていく。電卓ができ、変数が使え、関数が呼べ、ポインタが扱える。最終的には `printf` を呼んで「Hello, world」が書けるようになる。だが、骨格そのものはこの章で完成する。だから第1章は他のどの章よりも重要だ。**ここで使う道具と考え方が、最後まで通用する**。

そのため、この章だけは7つのサブ章に分けて、徹底的に丁寧に説明する。

| サブ章 | 内容 |
|--------|------|
| 00（この文書）| 章全体の見取り図と「動くもの」の確認 |
| 01 | 正規表現の基礎 — flex で使う最小限の知識 |
| 02 | flex 入門 + 字句解析器 `lexer.l` の詳説 |
| 03 | bison 入門 + 構文解析器 `parser.y` の詳説 |
| 04 | 抽象構文木とは何か + `ast.h` / `ast.c` の詳説 |
| 05 | x86 アセンブリ最小限 + `codegen.c` の詳説 |
| 06 | `main.c` と `Makefile` — 全体を組み上げる |

第2章以降はこんなに丁寧には説明しない。骨格が頭に入っていれば、新しく加わる機能の差分だけ追えば理解できるはずだ。だからこそ、ここをじっくりやる。

慌てず、迷子にならず、納得しながら進んでほしい。


## 1. まず動かしてみる

理屈の前に、まず「動くもの」を見るのが一番だ。完成形のコンパイラを動かして、何が起きるかを目で確認しよう。

ソースファイル `test.c` を用意する。

```c
int main() {
    return 42;
}
```

このコンパイラ `tinyc` に渡すと、x86 アセンブリが出てくる。

```bash
$ ./tinyc test.c
  .text
  .globl main
main:
  pushq %rbp
  movq %rsp, %rbp
  movl $42, %eax
  leave
  ret
```

たった7行。これがコンパイル結果のすべてだ。

このアセンブリを `gcc` に渡せば、実行ファイルになる。`gcc` はリンカ（プログラムをまとめる道具）と、アセンブラ（アセンブリを機械語に変える道具）を内部で呼んでくれる。

```bash
$ ./tinyc test.c > test.s
$ gcc -o test test.s
$ ./test
$ echo $?
42
```

`echo $?` は直前のプログラムの終了コードを表示するシェルの記法だ。`42` と出る。`return 42;` という C のソースコードが、本当に「終了コード 42 で終わるプログラム」になった。

これが**コンパイル**だ。人間が書いたソースコードを、CPU が実行できる形に変換する。tinyc がやっているのは、まさにそれだ。


## 2. もう一つの覗き穴 — `--dump-ast`

tinyc には `--dump-ast` というオプションがある。これを付けると、コンパイラが内部で作る木構造（**AST**, Abstract Syntax Tree）が表示される。

```bash
$ ./tinyc --dump-ast test.c
FUNC_DEF main
  BLOCK
    RETURN
      INT_LIT 42
```

ソースコード `int main() { return 42; }` が、この木に変換されている。

- 一番上は「関数定義 `main`」
- その中に「ブロック `{...}`」
- ブロックの中に「return 文」
- return 文の対象として「整数リテラル 42」

コンパイラは、ソースコードをまずこの木に変換し、それからこの木を辿ってアセンブリを生成する。**ソースコード → 木 → アセンブリ**、という二段階の変換だ。

```
ソースコード         木 (AST)              アセンブリ
"int main() {        FUNC_DEF main         main:
  return 42;            BLOCK                 pushq %rbp
}"                        RETURN              movq %rsp, %rbp
                            INT_LIT 42        movl $42, %eax
                                              leave
                                              ret
```

なぜわざわざ木を経由するのか。答えは「そのほうが楽だから」だ。文字列のままでは「`return` の後ろにある式」を取り出すのが面倒だが、木にしてしまえば「return ノードの子」と言えばすぐ取り出せる。コンパイラの中で扱いやすい形に一度変換しておくのだ。


## 3. これから作るファイル

第1章で書くファイルは全部で7つ。

```
src/
  ast.h       ノードの型定義
  ast.c       ノードを作る関数
  lexer.l     字句解析の規則（flex で書く）
  parser.y    構文解析の規則（bison で書く）
  codegen.h   コード生成のインターフェース
  codegen.c   コード生成
  main.c      エントリポイント
Makefile      ビルドの手順
```

役割分担はこうだ。

| ファイル | 何をする |
|---------|---------|
| `lexer.l` | ソースコードの**文字列**を**トークン**の列に変える |
| `parser.y` | トークンの列を**木 (AST)** に組み立てる |
| `ast.h` / `ast.c` | 木のノードの型と、ノードを作る関数 |
| `codegen.c` / `codegen.h` | 木を辿って**アセンブリ**を出力する |
| `main.c` | コマンドライン引数を処理し、上記をまとめて呼ぶ |
| `Makefile` | コンパイラ自身をビルドする手順 |

合計で約240行。これがコンパイラの全体だ。ライブラリでもフレームワークでもない、本物のコンパイラが、この行数で書ける。


## 4. 全体の流れ

7つのファイルがどう連携するか、データの流れを追ってみよう。

```
+-----------+
| test.c    |  人間が書いた C ソース
+-----+-----+
      |
      v
+-----------+
| lexer.l   |  flex がCコードを生成
| (lex.yy.c)|  → 文字列をトークンに分解
+-----+-----+
      | int, main, (, ), {, return, 42, ;, }
      v
+-----------+
| parser.y  |  bison がCコードを生成
|(parser.tab|  → トークン列から木を組み立てる
| .c)       |  途中で ast.c のコンストラクタを呼ぶ
+-----+-----+
      |
      v
+-----------+
| Node 木   |  メモリ上の AST
+-----+-----+
      |
      v
+-----------+
| codegen.c |  木を辿ってアセンブリを出力
+-----+-----+
      |
      v
+-----------+
| test.s    |  x86 アセンブリ
+-----------+
```

`lexer.l` と `parser.y` は、そのままでは C のコードではない。**flex** と **bison** という道具が、これらの定義ファイルから C のソースコード（`lex.yy.c`、`parser.tab.c`）を自動生成する。生成された C コードを、自分で書いた C コード（`ast.c`、`codegen.c`、`main.c`）と一緒にコンパイルすれば、`tinyc` というコンパイラ実行ファイルができる。

つまり、コンパイラを作るために、別のコンパイラ（gcc）と二つの自動生成ツール（flex、bison）を使う。これは普通のことだ。コンパイラ研究者が長年積み上げた道具を、我々はありがたく使わせてもらう。


## 5. 必要な前提知識

この章を読むのに必要な知識は次の通り。

- **C 言語の基礎**: 構造体、ポインタ、関数、`malloc`/`calloc` あたりが分かれば十分。
- **シェルの基本操作**: `cd`、`make`、`echo`、`./prog` などが使えれば十分。

逆に、**前提としない**ものは次の通り。これらはこの章の中で必要な分だけ説明する。

- 正規表現（→ サブ章 01 で説明）
- flex の使い方（→ サブ章 02 で説明）
- bison の使い方（→ サブ章 03 で説明）
- x86 アセンブリ（→ サブ章 05 で説明）

「アセンブリを書いたことがない」「flex/bison を使ったことがない」── 全く問題ない。むしろこの章は、そういう人が「ああ、こういうものだったのか」と納得することを目指して書いてある。


## 6. 動作環境

このコンパイラは **x86-64 Linux** をターゲットにしている。生成されるアセンブリは x86-64、呼び出し規約は System V AMD64 ABI。Linux 上で `gcc` を使ってビルド・実行できる。

Mac (Apple Silicon) や Windows でも、コンパイラ自体（`tinyc`）はビルド・動作する。コンパイラはアセンブリを「文字列として」吐き出すだけだから、どこで動かしてもよい。ただし、出てきたアセンブリを実際に実行ファイルに変換するには、x86-64 Linux 環境が必要だ。Docker や WSL を使うのが手軽だろう。

`--dump-ast` で AST を確認するだけなら、どんな環境でも動く。
